# AI Affiliate Factory — 要件定義 v1.0

**ステータス:** 設計確定用ドラフト（実装開始前の合意文書）  
**根拠:** 既存リポジトリ監査（`docs/repository-audit.md`）および本指示  
**関連:** `architecture-v1.0.md` / `data-model-v1.0.md` / `implementation-plan-v1.0.md`

---

## 1. 目的

AI Affiliate Factory は、記事生成単体ツールではない。

次を一連で行う **AI コンテンツ運営システム** である。

1. 情報収集  
2. 市場・流行・競合分析  
3. ネタ選定  
4. コンテンツ戦略決定  
5. コンテンツ生成  
6. 事実確認  
7. 品質レビュー  
8. 修正・再生成  
9. 公開先選定  
10. 公開  
11. 投稿結果・流入・反応の収集  
12. 次回の戦略・生成への反映  

**最優先目的:** 開発それ自体ではなく、アフィリエイト収益につながるコンテンツ運営を、可能な範囲で自動化すること。

## 2. スコープ

### 2.1 初期対象（In scope — Phase 近傍）

| 領域 | 初期方針 |
| --- | --- |
| 収益ジャンル | アダルト系アフィリエイト |

| 公開先 | **Blogger**（長文・検索・導線）、**X**（拡散・育成・流入） |
| 動画生成 | **対象外**（将来拡張として構造のみ考慮） |
| 運用言語 | 主に日本語（X は原則全角 140 文字以内で成立） |
| 技術基盤 | 既存 monorepo（TypeScript / Node 24+ / pnpm / PostgreSQL / Prisma）を継承 |

### 2.2 将来対象（Out of initial delivery, in architecture）

- 海外アダルト系 ASP・販売サイト  
- 公開先: note / Threads / Instagram / Pinterest / TikTok / YouTube Shorts / その他 CMS・Web

- 管理画面 UI  
- 高度な自動運用（条件付き自動公開の拡大）  
- 有料 Social / Analytics API の本格接続（必須にしない）

- 動画生成パイプラインの実装  
- 無制限・無差別クローリング

- API 承認済み前提の本番依存  
- 全処理を単一巨大サービスに集約する再設計  
- この文書フェーズでの大規模機能実装

## 3. 確定要件（Must）

### 3.1 システム性質

1. リサーチ → 戦略 → 生成 → 事実確認 → レビュー → 公開先選定 → 公開 → 計測 → 学習、のライフサイクルを持てる。  
2. ASP・情報源・公開先・LLM・分析・通知は **差し替え可能な境界** を持つ（専用構造への固定禁止）。  
3. API 未承認でも Mock／手動登録で縦切り検証できる。  
4. 根拠（出典・事実・評価・プロンプト・モデル実行）を残し、AI の結論だけを保存しない。  
5. 成人向け・各プラットフォーム規約は **Policy Rule として更新可能**（全面ハードコード禁止）。

### 3.2 公開先役割（初期）

**Blogger**

- 長文・比較・紹介・解説・ランキング  
- 検索流入、X からの受け皿、アフィリエイト導線  

**X**

- 拡散・注目・Blogger 流入・アカウント育成  
- トレンド性・短く価値を伝える情報  
- 原則 **日本語全角 140 文字以内**で本文が成立すること  
- 本文に収まる場合は不要な返信を付けない  
- 不足時のみ、比較／公式／根拠／有用情報を返信で追加（「続きはこちら」のみ等の低価値返信は禁止）

### 3.3 品質・修正

- 一度の LLM 出力をそのまま公開しない。  
- 修正回数の固定上限を設計の中心にしない。  
- 改善量・失敗理由の反復・コスト・時間による停止条件を持つ。  
- 部分修正／構成変更／全面再生成／切り口変更／公開先変更／追加リサーチ／保留／破棄を選択できる。

### 3.4 公開頻度・承認

- 初期目安: Blogger + X 合計 **1日 1〜2 回**（機械的必達ではない）。  
- 固定 cron のみに依存せず、**公開キュー**で制御できる。  
- 自動／条件付き自動／人間承認後／常に下書き、をコンテンツまたは公開先単位で選べる。  
- 公開ライフサイクル状態を持つ（§17 相当。名称は実装で既存 enum と整合）。

### 3.5 学習・評価

- 取得可能指標＋手動／CSV／将来 API を許容。欠損は null／未取得。  
- 媒体・目的・アカウント規模・経過時間で正規化可能な評価を検討する。  
- X API 有料利用を初期必須にしない。

### 3.6 ジョブ・コスト

- 長時間処理を単一 HTTP リクエストに閉じない。  
- 再試行・冪等・重複防止・部分失敗・優先度・履歴を扱える。  
- LLM／API／リサーチ等のコストを追跡し、予算超過時に安全側へ倒せる。

## 4. 機能要件

### FR-01 アフィリエイトプロバイダ

- API / フィード / 手動インポート / 公開ページ取得を、可能な範囲で **共通内部商品表現** に正規化する。  
- DMM／FANZA 専用テーブル名・サービス名にシステム全体を固定しない。  
- 既存 FANZA Provider は第一実装アダプターとして再利用する。

### FR-02 情報源・リサーチ

- Source Adapter を追加可能にする。  
- robots.txt / 利用規約 / API 規約 / レート制限 / 著作権 / 個人情報 / 重複 / コスト / 鮮度を考慮する。  
- 競合取得件数を固定しない。探索は目的・時間・コスト・重複・信頼度による **動的終了条件** を持つ。

### FR-03 ネタ選定・コンテンツ形式

- 形式を enum 分岐の無限増殖だけで増やさない。  
- 処理制御に必要な **最低限の Content Type** は定義する（既存: blog / x-post / short-video-script / product-introduction 等を拡張可能に整理）。  
- 市場・競合・検索・SNS・過去実績に基づき形式を選択する。

### FR-04 コンテンツ戦略

戦略オブジェクトに最低限含める:

- テーマ、読者、意図、目的、想定公開先、形式、切り口  
- 使用する事実・出典、競合差分、アフィリエイト導線、CTA  
- 画像・埋め込み、公開タイミング、成功判定指標  

「Strategy AI」1 クラスへの全責任集中は避ける。

### FR-05 事実（Claim）管理

各事実について追跡:

- 主張、出典、情報源種別、取得日時、公開日時（分かる場合）  
- 引用／要約、複数ソース一致、公式／第三者、信頼度、鮮度／有効期限  
- 使用したコンテンツへの関連  

単一ソース・意見・推測・公式・客観事実を区別する。

### FR-06 生成パイプライン

Research → Strategy → Outline → Draft → Fact-check → Competitor compare → Quality review → Revision plan → Patch/Regenerate → Re-evaluate → Publish readiness → Publish

役割・プロンプト・入出力・評価を記録する（モデル固定は必須としない）。

### FR-07 公開先選定・Publisher

- 全媒体への強制同時投稿をしない。  
- Publisher Adapter 共通インターフェース。  
- 初期: BloggerPublisher / XPublisher（既存 X 実装を Adapter 化して吸収）。

### FR-08 計測・アフィリエイト成果

- プラットフォーム指標＋アフィリエイト（クリック／発生／確定／売上等）。  
- 投稿と成果の弱い紐付け（日付・商品・流入経路）を許容し、過度なアトリビューションを仮定しない。

### FR-09 SEO（Blogger 記事単位の基本）

タイトル、見出し、meta description、URL、内部リンク、検索意図、重複防止、構造化、FAQ、alt、更新日、canonical、noindex 判断。  
高度 SEO 戦略の自動確立は前提にしない。専門家ルールを設定として取り込める。

### FR-10 管理・運用

CLI と Admin API / Operations Console（P7）で、候補・戦略・事実・レビュー・公開・実績・コスト・設定・停止を操作できる。  
P6 までは CLI 中心、P7 で内部管理 API + Web を追加（一般ユーザー向け画面ではない）。両者は同一 Application Service を利用する。

### FR-11 本番配線（P8）

- 実 LLM / 実 Blogger は `*_MODE=api` かつ `*_ALLOW_EXTERNAL_REQUESTS=true` のときのみ接続する。  
- Quality Gate で schema / Claim / fact / writing / Policy / CTA を評価し、fallback は自動公開しない。  
- `PRODUCTION_OPERATION_MODE=ASSISTED` を初期とし、Blogger Draft は承認後、公開と X 投稿は手動。  
- Budget stop で生成・Review・Revision を止め、Job を `BUDGET_BLOCKED` 相当で失敗扱いにする。

## 5. 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-01 | Node.js 24+、pnpm workspace monorepo、PostgreSQL、Prisma を維持 |

| NFR-07 | レート制限・予算・kill switch による安全停止 |
| NFR-08 | 監査ログ（誰が何を承認／公開／停止したか） |

## 6. 成人向けコンテンツの制約

- 18 歳未満を扱わない／未成年誤認表現を避ける  
- 違法コンテンツ・無断転載禁止  
- 商品・サンプル画像の利用条件確認  
- ASP / Blogger / X 等の規約遵守  
- 広告・アフィリエイト表記  
- 地域・公開先ごとの成人表示制限  
- 禁止ワード・禁止ジャンル  
- 公開停止・削除要求への対応  

→ **Policy Rule**（設定／DB）として更新可能にする。コードへの全面ハードコードは禁止。

## 8. API 未承認時の対応

1. `MockResearchProvider`／手動インポートで商品・メトリクスを投入  
2. Content／Strategy／Review をローカル DB で完走  
3. Publisher は Mock（X Mock／Blogger Mock）。実 Blogger は P4.5 明示設定時のみ  
4. LLM は Mock 既定。本番 LLM は `LLM_MODE=api` 等の明示設定時のみ  
4. 実 API フラグは既定 off（既存: `X_API_ENABLED=false` 等）  
5. 承認後に Adapter 実装を差し替え、正規化スキーマは変えない

## 9. 成功指標

### 9.1 プロダクト成功（事業）

- 承認取得・媒体育成に寄与する公開の継続  
- アフィリエイトクリック／成果の増加（取得可能な範囲）  
- 規約違反・凍結・スパム判定の回避  

### 9.2 システム成功（技術）

- Mock のみで Research→Publish→Metrics の縦切りが再現可能  
- 新規 ASP／Publisher 追加が既存コアを壊さず Adapter 追加で可能  
- 事実・出典なしの公開がガードされる  
- コスト／予算超過時に自動投稿が止まる
